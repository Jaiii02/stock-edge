# StockEdge 30-Day Full-Stack Development Plan

This plan turns the current StockEdge prototype into a more reliable, production-shaped full-stack application.

The goal is not to rewrite everything at once. Each phase should leave the application working so that progress is easy to verify and undo.

## Target architecture

```text
React frontend
    ↓
Typed API client
    ↓
FastAPI routes
    ↓
Analysis service
    ↓
PostgreSQL + cached market data
    ↓
Yahoo Finance / future data providers
```

The CSV should become a one-time seed/import source. PostgreSQL should become the runtime source of truth for companies, industries, cached metrics, analysis history, and future user features.

## Database direction

Use PostgreSQL as the long-term database, SQLAlchemy for Python database access, and Alembic for schema migrations.

Start with these tables:

- `companies`: symbol, name, industry, ISIN, series, active status
- `industries`: industry names and identifiers
- `fundamental_snapshots`: dated fundamental metrics and their source
- `valuation_snapshots`: dated valuation metrics and their source
- `analysis_runs`: scores, recommendation, confidence, timestamp, and scoring-model version

Add later:

- `price_history`
- `technical_snapshots`
- `users`
- `watchlists`
- `watchlist_items`

## Day 1 — Create a safe checkpoint

- [x] Create the first Git commit.
- [x] Add a proper root `.gitignore`.
- [x] Ignore `backend/venv`, `__pycache__`, `*.pyc`, `node_modules`, `dist`, and `.env` files.
- [x] Write down the commands required to run the frontend and backend.
- [x] Confirm the current application still loads before making changes.

## Day 2 — Define the first product version

- [x] Define the target user: long-term Indian-equity investor.
- [x] Define what each recommendation means.
- [x] Decide how fresh financial data must be.
- [x] Decide what happens when data is missing or stale.
- [x] Define the first promise: analyze a supported NSE stock, compare it with peers, and explain the result.
- [x] Avoid promising perfect investment advice.

## Days 3–4 — Clean up the backend structure

Gradually move from the current flat backend to an application package:

```text
backend/app/
├── main.py
├── api/
├── core/
├── db/
├── schemas/
├── services/
└── providers/
```

- [x] Add proper Python package files and stable imports.
- [x] Move route definitions into API modules.
- [x] Move configuration into `core/config.py`.
- [x] Keep financial calculations intact while moving files.
- [x] Verify the backend after each structural change.

## Days 5–7 — Add PostgreSQL and import the CSV

- [ ] Run PostgreSQL locally or through Docker.
- [ ] Install and configure SQLAlchemy.
- [ ] Configure Alembic migrations.
- [ ] Create the `companies` and `industries` tables.
- [ ] Write a one-time CSV import script.
- [ ] Move the CSV to `backend/data/seed/`.
- [ ] Change `/symbols` to read from the database.
- [ ] Change peer lookup to query companies by `industry_id`.
- [ ] Add unique constraints for symbols and industry names.
- [ ] Add indexes for symbol and industry lookups.

## Days 8–10 — Define a real API contract

- [ ] Create Pydantic request and response models.
- [ ] Add an `/api/v1` prefix.
- [ ] Create routes such as:
  - `GET /api/v1/health`
  - `GET /api/v1/stocks`
  - `GET /api/v1/stocks/{symbol}`
  - `GET /api/v1/stocks/{symbol}/analysis`
- [ ] Return `404` for unknown symbols.
- [ ] Return `503` when external market data is unavailable.
- [ ] Validate symbols before analysis.
- [ ] Make success and error responses predictable.
- [ ] Keep the API documentation generated by FastAPI understandable.

## Days 11–13 — Make market-data fetching reliable

- [ ] Create a `MarketDataProvider` interface.
- [ ] Put Yahoo Finance code inside `YahooFinanceProvider`.
- [ ] Add timeouts and controlled retries.
- [ ] Add logging around provider calls.
- [ ] Store the latest successful metrics in snapshot tables.
- [ ] Record `source`, `fetched_at`, and `as_of_date`.
- [ ] Read recent cached data before requesting fresh data.
- [ ] Decide what to do when the cache is stale.
- [ ] Avoid fetching every peer from Yahoo Finance for every user request.

Preferred flow:

```text
User request
    ↓
Read recent cached metrics
    ↓
Run analysis quickly
```

Separate refresh work can update the cache later.

## Days 14–16 — Stabilize the scoring engine

- [ ] Move metric directions and weights into a clear configuration.
- [ ] Handle negative P/E values explicitly.
- [ ] Handle zero denominators.
- [ ] Handle missing-all-metrics cases.
- [ ] Handle stocks with no peers.
- [ ] Decide how to treat extreme outliers.
- [ ] Check whether all peers use compatible reporting periods.
- [ ] Add a scoring-model version such as `business-quality-v1`.
- [ ] Save that version with every analysis run.
- [ ] Keep scoring functions deterministic and easy to test.

## Days 17–19 — Add automated tests

Create backend tests with deterministic fixtures:

- [ ] Peer lookup
- [ ] Symbol validation
- [ ] Missing-data handling
- [ ] FCF conversion
- [ ] Net debt/EBITDA
- [ ] Percentile ranking
- [ ] Business score weighting
- [ ] Valuation score calculation
- [ ] Recommendation thresholds
- [ ] Confidence calculation
- [ ] API error responses

Mock Yahoo Finance in tests. Tests should not depend on the internet.

Later add frontend tests for loading, success, error, empty states, and analysis rendering.

## Days 20–22 — Improve the frontend experience

Create explicit UI states:

```text
idle → loading → success
              ↘ error
              ↘ empty
```

- [ ] Check `response.ok` before parsing a successful response.
- [ ] Prevent error objects from reaching successful-analysis rendering code.
- [ ] Show a useful connection or data error message.
- [ ] Add retry behavior.
- [ ] Move the API URL to `VITE_API_BASE_URL`.
- [ ] Create a small API client instead of hardcoding URLs in components.
- [ ] Add a `useStockAnalysis` hook.
- [ ] Debounce autocomplete requests if the API becomes remote.
- [ ] Add keyboard navigation for suggestions.
- [ ] Add proper labels and accessible controls.
- [ ] Add skeleton loading states.
- [ ] Make cards responsive on mobile.
- [ ] Display last-updated timestamps.
- [ ] Explain confidence and missing data clearly.

Start with React state and custom hooks. Add a server-state library only when caching and refetching become difficult to manage manually.

## Days 23–25 — Add technical analysis carefully

Do not add many indicators at once.

Start with:

- [ ] Price trend
- [ ] 50-day moving average
- [ ] 200-day moving average
- [ ] Momentum
- [ ] Relative strength versus Nifty
- [ ] Volume confirmation

Keep the layers separate:

```text
Business Quality → Is this a good company?
Valuation        → Is it attractively priced?
Technical Trend  → Is market behavior supportive?
Macro Context    → Is the environment favorable?
```

Technical signals should not silently change fundamental metrics.

## Days 26–27 — Improve explainability

Replace simple messages with evidence:

- [ ] Show the actual metric value.
- [ ] Show the peer percentile.
- [ ] Show the peer median.
- [ ] Explain whether the metric helped or hurt the score.
- [ ] Show data freshness.
- [ ] Show missing-data warnings.
- [ ] Explain how the final recommendation was calculated.

Example:

```text
ROE: 24.2%
Peer percentile: 88th
Effect: Strong positive contribution
```

## Priority order

### Highest priority

1. Git checkpoint and `.gitignore`
2. Backend error handling
3. API response schemas
4. Database migration
5. Cached market data
6. Scoring tests
7. Frontend loading and error states
8. Environment-based configuration

### Medium priority

1. Better project structure
2. Technical analysis
3. Explainability improvements
4. Analysis history
5. Responsive design
6. Data freshness display
7. Logging and monitoring

### Later

1. User accounts
2. Watchlists
3. Notifications
4. Macro analysis
5. Portfolio tracking
6. Advanced charts
7. Personalized recommendations
8. Machine-learning predictions

## Do not add yet

Avoid these until the core application is reliable:

- Microservices
- Kubernetes
- Redis
- Celery
- GraphQL
- Machine learning
- Complex authentication
- WebSockets
- Multiple databases
- Large UI component libraries

## First major milestone

The first production-shaped milestone is:

> A user can search for a stock, receive a fast analysis from cached database data, see a clear loading or error state, understand when the data was updated, and receive a fully validated API response.

Once this works, technical analysis, macro analysis, watchlists, and deployment can be added much more safely.
